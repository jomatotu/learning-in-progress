## Step 3: Build

Write ONE complete, self-contained HTML document.

Hard technical rules, because it runs in a locked-down sandboxed iframe:
- All CSS and JavaScript inline. No external scripts, stylesheets, fonts, images, CDNs, or fetch/XHR/WebSocket calls; they are blocked and the page will break.
- Images only as inline SVG, canvas, or data: URIs.
- No localStorage, sessionStorage, cookies, or IndexedDB (they throw in the sandbox). Keep state in JavaScript variables.
- No alert(), confirm(), prompt(), window.open(), or form submissions. Show messages inside the page.
- Must work offline in current Chrome, Edge, Safari, and Firefox. No build step, no frameworks.
- Keep it under about 200 KB.

Accessibility rules:
- Calm, uncluttered layout. One main thing on screen at a time. No flashing; any animation is short and can be turned off.
- Readable text: sans-serif system font stack, at least 18px, line height 1.5 or more, left-aligned, lines no longer than about 70 characters, no italics or all caps for body text.
- High contrast on a soft off-white background. Don't rely on color alone to show right or wrong.
- Large click targets, full keyboard support, visible focus, semantic HTML, and ARIA labels. Announce feedback with aria-live.
- Plain, friendly, encouraging language with short sentences. Mistakes get a neutral correction and the reason, never a penalty.
- The student controls the pace: next and back buttons, nothing auto-advances.

Common bugs to avoid (learned from earlier pages):
- Text size: set html { font-size: 18px } and keep every text size at 1rem or more. Sizes like 0.9rem, or a mobile media query that shrinks the root font, drop below 18px.
- After an answer, mark options with aria-disabled="true" and an "answered" flag, not the disabled attribute. disabled removes the focused button from the tab order and keyboard users get lost.
- A hidden button still runs its click handler. Start every forward handler with a guard (if the button is hidden or aria-disabled, return).
- One forward control per screen. Don't show the global Next button and a quiz's own "next question" button at the same time.
- Feedback always gives the reason in one short sentence, not just "right" or "not yet". Mark right and wrong with a symbol and a word as well as color, and prefer teal and purple over green and red.
- Progress is written as text, such as "Step 3 of 6", not only as colored segments.
- Remember each quiz answer by question number, and show the stored answer when the student comes back with Back, so nothing is counted twice.
- Phone width (390 px): rows of buttons use flex-wrap: wrap, and button labels stay short. Don't use tables with several columns; use short labeled blocks (dl) instead.
- No text inside SVG diagrams, because it becomes unreadable on small screens. Put labels in HTML under the figure, and limit figures to about 26rem wide.
- A focused heading after a screen change gets h2:focus { outline: none }, so no stray box appears around it.
- Read-aloud (speechSynthesis): where no voice is installed, onend may never fire and onerror fires at once. Add a timer guard that moves on, and show a visible message in its own element instead of leaving a dead button.

Content rules:
- Cover every key idea of the material or topic. Don't drop important facts. List the facts of the material first and check each one off as you build, including "boring" ones such as units, percentages, and named effects.
- Quiz the common misconceptions, not only definitions.
- Don't invent facts. Analogies and interest-based examples are fine if they're clearly examples.
- Write all text the student sees in the same language as the material.

At the top of the page, add a small collapsible section titled "Why it looks like this" (translated into the student's language) that explains in 2 to 4 short sentences, addressed to the student, why this design fits them, using the evidence from Step 2 with short source names.

Don't use any tools: no terminal, files, scripts, browser, or web search. Write the page straight into your reply.

Before you reply, check the page in your head by reading it once: the script has no syntax errors, every button has a working handler, and none of the blocked APIs or http(s) links from the rules above appear.
